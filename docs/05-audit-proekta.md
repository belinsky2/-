# Аудит проекта и плана разработки

Полная проверка документов 01–04 на соответствие целям и сценариям использования.
Метод: каждое решение сверялось с (а) целью — личная цифровая тетрадь по методике Картер,
(б) сценариями — захват идеи на ходу, рант голосом, воркшоп вечером, сцена, разбор после
выступления, (в) заявленным будущим — Mac-синк, смена телефона, раздача знакомым.

**Вердикт: фундамент верен, сносить нечего.** Доменная модель, машина состояний,
петля «сцена → оценка → пересборка акта», порядок этапов, схема доставки через CI,
подготовка слоя данных к слиянию — всё выдерживает проверку. Найдено: 3 внутренних
противоречия между документами, 3 места избыточного усложнения и 3 недооценённых риска.
Все правки применены к документам 01, 03, 04 этим же коммитом.

---

## 1. Противоречия между документами (исправлены)

### 1.1. Шифрование БД против экспорта и синка
Документ 01 требовал «шифрование локальной БД». Документ 04 при этом описывает экспорт
хранилища в открытом виде и синк через общую папку Syncthing — то есть те же данные
всё равно лежат расшифрованными рядом. SQLCipher добавил бы зависимость, усложнил бэкап
и не защитил бы ничего сверх того, что уже даёт системное шифрование Android (FBE),
включённое на S24 Ultra по умолчанию.
**Решение:** отдельного шифрования БД нет. Модель защиты: системное шифрование устройства +
приложение без сети + бэкап-файл хранится там, куда его положил владелец. Честно и проще.

### 1.2. Профиль в DataStore против переноса данных
Документ 03 отправлял профиль (цель по минутам, comedy vision, история шкалы смешного)
в DataStore. Но формат переноса из документа 04 — `vault.sqlite` + блобы. DataStore в него
не входит: при смене телефона профиль молча терялся бы.
**Решение:** всё, что создал пользователь и что должно пережить смену телефона, живёт в Room.
DataStore — только для локальных мелочей устройства (последняя открытая вкладка и т.п.),
потеря которых незаметна.

### 1.3. Разрешение конфликтов: «на уровне поля» против «на уровне записи»
Документ 01 обещал last-write-wins по полям, документ 04 — по записям. Побеждает вариант 04:
по записям, с сохранением проигравшей версии в `BitVersion`. Слияние по полям для шутки
опасно содержательно: премиса от одной правки и панч от другой могут вместе не иметь смысла.

## 2. Избыточные усложнения (срезаны)

### 2.1. Mind-map как холст с координатами → структурированный список
`MindMap` с узлами `x, y` и жестами S Pen — самый дорогой экран всего проекта
(недели работы на кастомный canvas), при том что методике важно **ветвление ассоциаций**,
а не их расположение на плоскости. Свободный холст — главный кандидат похоронить проект
на этапе M2, а риск №1 в плане — «перегрузить и бросить».
**Решение:** в v1 mind-map — это дерево-аутлайн (вложенный список со свайпами и
промоушеном узла в шутку). Координаты из модели убраны. Холст — возможное улучшение потом,
модель дерева от этого не изменится.

### 2.2. Полная KMP-обвязка в v1 → дисциплина вместо инфраструктуры
M0 требовал `:core:data` «KMP-совместимым» сразу. Реально это тянет bundled-драйвер SQLite,
KMP-таргеты в Gradle и решение проблем, которые понадобятся только в v2.
**Решение:** в v1 — три модуля, но по-простому: `:core:model` — чистый Kotlin (жёстко,
без единого Android-импорта), `:core:data` — обычная Android-библиотека, в чьих сущностях
и DAO запрещены Android-типы (`Context`, `Uri`, `Parcelable`). Это бесплатная дисциплина,
которая делает перевод на KMP в v2 механическим. Сама KMP-конфигурация — тогда же.

### 2.3. Статус `ready` → вычислимое состояние
`ready` («стоит в сет-листе») дублировал факт, который и так виден по связи
`SetListItem → Bit`. Хранимый статус, повторяющий связь, гарантированно рассинхронизируется
(шутку убрали из сета — статус остался).
**Решение:** жизненный цикл хранит `seed → premise → draft → tested → polished`
(+ `parked`/`retired`), а «в сете / ждёт прогона» — вычисляется из связей и показывается
бейджем. Меньше состояний — меньше багов.

## 3. Недооценённые риски (теперь учтены)

### 3.1. Транскрипция длинных рантов — главный технический риск v1
`SpeechRecognizer` спроектирован под короткие фразы: на непрерывном 2–3-минутном ранте
он обрывается по тишине, сессии приходится перезапускать и склеивать, офлайн-модель ru-RU
на устройстве может требовать докачки и даёт заметно худшее качество, чем онлайн.
Архитектура это уже переживает (аудио первично, транскрипт вспомогателен), но план
обещал транскрипцию слишком уверенно.
**Решение:** в M2 транскрипт официально best-effort: сегментированная запись, явная кнопка
«распознать ещё раз». Путь апгрейда — whisper.cpp на устройстве (S24 Ultra потянет),
вынесен в задел v1.5, а не вшит в критический путь.

### 3.2. Экспорт папкой через SAF — медленно; синк-папка упрётся в scoped storage
Экспорт «папки с сотнями блобов» через SAF/DocumentFile печально известен скоростью
(секунды на файл). А для v2-синка вольём-папка должна быть доступна стороннему Syncthing,
который не умеет писать в приватные каталоги приложений на современном Android.
**Решение:** бэкап в v1 — **один ZIP-файл** через `ACTION_CREATE_DOCUMENT` (внутри тот же
формат: manifest + vault.sqlite + blobs/). Для v2 зафиксирован открытый вопрос: синк-папка
выбирается пользователем через SAF с persist-разрешением, и приложение зеркалит туда
журналы; решается при проектировании `:core:sync`, не сейчас.

### 3.3. Мелочи, которые сорвали бы этап, всплыв внезапно
- `POST_NOTIFICATIONS` — runtime-разрешение с Android 13: напоминание об утренних страницах
  без него молча не покажется. Добавлено в M3.
- `minSdk 30 → 26`: для самого S24 Ultra разницы нет, но раз раздача знакомым — заявленный
  сценарий, три версии Android запаса стоят примерно ноль усилий на Compose.
- Obtainium с приватным репозиторием требует GitHub-токен у получателя. Либо репозиторий
  с релизами публичный, либо получателям APK пересылается файлом. Отмечено в плане.
- Справочник упражнений редактируемый, но сеется из `assets/exercises.json`: при обновлении
  приложения пользовательские правки не должны затираться. Правило: сид применяется только
  к записям, которые пользователь не трогал (флаг `userEdited`).

## 4. Проверка покрытия сценариев

| Сценарий | Покрыт | Где |
|---|---|---|
| Идея в метро за 3 секунды | ✅ | M1: FAB + App Shortcut, аудио/текст |
| Утренние страницы по напоминанию | ✅ | M3 (+ разрешение уведомлений — п. 3.3) |
| Рант голосом без остановки | ✅ | M2, с учётом п. 3.1 |
| Вечерний разбор Inbox | ✅ | M2: визард seed → draft |
| Сцена: тёмный зал, cue-слова, запись | ✅ | M4 |
| Разбор после выступления одним тапом | ✅ | M5 |
| Репетиция | ✅ | Gig(type=rehearsal) + чеклист упр. 30 |
| Смена телефона | ✅ | M1.5, теперь одним ZIP |
| Раздача знакомым | ✅ | M0: keystore, имя пакета; п. 3.3 про Obtainium |
| Mac в будущем | ✅ | Дисциплина модулей (п. 2.2) + формат хранилища |

Один разрыв в UI-логике: метрики («главный экран») были описаны, но среди пяти вкладок
главного экрана не было. **Решение:** первая вкладка становится «Сегодня» — цепочка,
сегодняшний шаг практики, Inbox; список 48 упражнений живёт внутри неё вторым уровнем.
Пять секций тетради при этом никуда не деваются — «Практика» и «Дневник» объединены
навигационно, как и в бумажной тетради упражнения и утренние страницы соседствуют.

## 5. Что проверено и осталось без изменений

- **Стек**: Kotlin/Compose/Room/Media3 — без замечаний; альтернатив, лучших под цели, нет.
- **Отказ от Hilt, Firebase, аналитики, серверов** — подтверждён: каждый кандидат
  проверен вопросом «что сломается без него?» — ответ «ничего».
- **Манифест без `INTERNET`** — подтверждён, включая v2-синк через папку.
- **Порядок этапов** M0 → M1 → M1.5 → M2…M6 — подтверждён; каждый даёт рабочий APK.
- **Доставка через GitHub Actions** — подтверждена как единственный канал из этого
  окружения (блокировка dl.google.com перепроверена).
- **Пять решений слоя данных** (UUIDv7, tombstones, updatedAt/deviceId/lamport,
  SHA-256-блобы, MutationSink) — подтверждены; ни одно не избыточно для заявленного будущего.
- **Юридическая модель** «пустая тетрадь без текстов Картер» — подтверждена, критична
  для сценария раздачи.
