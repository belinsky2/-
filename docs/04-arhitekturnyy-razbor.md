# Архитектурный разбор после уточнения требований

Появилось новое требование: **синхронизация с приложением на Mac в будущем + смена телефона
без потери данных**. Это не косметика — оно ломает одно из ключевых допущений плана.
Ниже честный разбор: что выстояло, что нет, и что нужно изменить **сейчас**, пока не написан код.

---

## 1. Вердикт коротко

Доменная модель и продуктовая логика (документ 01) — верны, менять не нужно.
**Слой данных спроектирован неверно** для новых требований. Пять конкретных решений
надо принять до первой строки кода: они стоят несколько часов сейчас
и переписывания всего хранилища потом.

Главная ошибка в документе 03 — формулировка **«синхронизация не нужна → приложению
не нужен `INTERNET`»**. Первое было верно как решение для v1, второе я подал как
постоянное свойство архитектуры. Это преждевременный вывод, и он же самый дорогой:
«сделаем локально, синк прикрутим потом» — классическая ловушка.

Хорошая новость: цель «приложение никогда не ходит в сеть» **достижима даже с синхронизацией** —
см. раздел 5.

---

## 2. Что в архитектуре остаётся верным

| Решение | Почему держится |
|---|---|
| Доменная модель Topic → Bit → BitVersion → BitPerformance | Ложится на методику один-в-один, от требований синка не зависит |
| Машина состояний шутки | Ядро ценности продукта |
| Декларативные формы для 48 упражнений | Спасает от 48 экранов; данные форм — обычные записи, синкуются как всё остальное |
| Kotlin + Compose + Room | Room с версии 3.x умеет Kotlin Multiplatform — то есть тот же слой данных поедет на Mac |
| Offline-first, аудио как первичный ввод | Не меняется |
| Ручной DI вместо Hilt | Не меняется |
| Отказ от Firebase/аналитики | Не меняется |

## 3. Что неверно — пять обязательных изменений

### 3.1. Идентификаторы: автоинкремент → UUIDv7
Room по умолчанию раздаёт `Long` с автоинкрементом. Два устройства независимо создадут
`Bit(id=42)`, и при первом же слиянии одна шутка затрёт другую.
**Решение:** первичный ключ — `String`/`ByteArray` с UUIDv7 (упорядочен по времени, поэтому
не разрушает локальность индекса, в отличие от UUIDv4). Генерируется на устройстве, глобально уникален.

### 3.2. Удаление: физическое → надгробия (tombstones)
Удалённая на телефоне шутка при слиянии с Mac «воскреснет»: на Mac записи нет, значит
она выглядит как новая.
**Решение:** `deletedAt: Long?` во всех сущностях, все запросы фильтруют по `deletedAt IS NULL`.
Физическая чистка — раз в год, вручную, после успешного бэкапа.

### 3.3. Время изменения: нет → `updatedAt` + `deviceId`
Без этого невозможно разрешить конфликт «на телефоне и на Mac поправили одну шутку».
**Решение:** в каждой записи `updatedAt` (Unix ms), `deviceId` (UUID устройства, создаётся
при первом запуске) и счётчик `lamport` для устойчивости к перекосу часов.
Стратегия слияния — last-write-wins на уровне записи, но **проигравшая версия сохраняется
в `BitVersion`**, а не выбрасывается. Для тетради с шутками потерять текст недопустимо,
а вот показать «была ещё вот такая версия» — нормально.

### 3.4. Аудио: файлы по имени → адресация по содержимому
`rant_2026_03_14.m4a` при слиянии двух устройств — гарантированный конфликт имён,
а при повторном импорте — дубликаты на гигабайты.
**Решение:** имя файла = SHA-256 его содержимого, раскладка `blobs/ab/abcdef….m4a`,
в БД хранится хеш. Даёт бесплатно: дедупликацию, проверку целостности бэкапа,
слияние без конфликтов (одинаковый файл = одинаковое имя = нечего решать).

### 3.5. Мутации: россыпь DAO-вызовов → одна воронка
Позже понадобится журнал операций (для слияния и для истории). Если к тому моменту
запись в БД идёт из пятидесяти мест, добавление журнала — это правка пятидесяти мест.
**Решение:** все изменения проходят через единый `MutationSink`, который проставляет
`updatedAt`/`lamport` и (в будущем) пишет строку в `op_log`. Сейчас это ~50 строк кода,
потом — один файл вместо рефакторинга всего приложения.

> **Чего сознательно НЕ делаем сейчас:** самого журнала операций, CRDT, движка слияния.
> Это преждевременно. Мы делаем ровно то, что делает их возможными — и не более.

## 4. Раздача приложения (вопрос 1)

**Технически — просто.** Ссылка на APK в GitHub Releases, получатель разрешает установку
из неизвестных источников (в One UI: Настройки → Приложения → Особый доступ), жмёт «Всё равно
установить» на предупреждение Play Protect. Это одна минута.

Но три решения нужно принять **на этапе M0**, иначе раздача позже станет болезненной:

| Решение | Если не сделать сейчас |
|---|---|
| **Свой release-keystore** (не debug), ключ и пароли — в GitHub Secrets, копия — в менеджере паролей | Android принимает обновление только от APK, подписанного тем же ключом. Смена ключа = получателю (и тебе) придётся **удалить приложение вместе со всеми данными** и поставить заново |
| **Финальное имя пакета** `ru.punchline.workbook` | Имя пакета — вечный идентификатор приложения. Смена = другое приложение, данные не переносятся |
| **Все строки в `strings.xml`**, никакого русского текста в коде | Добавление второго языка позже — вычёсывание строк по всему коду. Сейчас это просто дисциплина, стоит ноль |

**Юридический момент, который стоит проговорить.** Пока раздаёшь друзьям — вопрос
не стоит. Но решение из документа 02 — *названия упражнений и промпты пользователь вносит
сам, в поставку они не входят* — принималось из-за неполноты источников, а оказывается
именно тем, что делает раздачу чистой. Приложение — пустая структурированная тетрадь, а не
пересказ книги Картер. **Это решение теперь надо защищать сознательно:** не соблазняться
«зашью 48 названий и 30 промптов в assets, так удобнее». Удобнее — да, но тогда
раздавать приложение уже нельзя.

Автообновления для получателей: **Obtainium** — ставится на Android, следит за GitHub
Releases и обновляет. Ничего не нужно писать самому.

Google Play — отдельный проект (аккаунт $25, политика конфиденциальности, требования
к target API, модерация). Не нужен, пока речь о десятке людей.

## 5. Синхронизация и смена телефона (вопрос 2)

**Это две разные задачи, и их надо решать по отдельности.**

### 5.1. Смена телефона — решается сейчас и дёшево
Нужен экспорт/импорт полного хранилища. Это уже было в плане, но стояло **последним этапом (M6)** —
и это ошибка приоритизации: потерять год материала из-за того, что бэкап отложили на конец,
и есть худший возможный исход проекта. **Переношу на позицию сразу после M1.**

Формат хранилища (он же — будущий формат обмена с Mac):

```
punchline-vault/
├── manifest.json     # schemaVersion, appVersion, deviceId, exportedAt, счётчики
├── vault.sqlite      # все текстовые данные — единицы мегабайт даже за годы
└── blobs/
    └── ab/abcdef…m4a # аудио по SHA-256, гигабайты
```

Разделение текста и аудио — не косметика: текстовая часть маленькая и синхронизируется
всегда, аудио тяжёлое и синхронизируется выборочно (или не синхронизируется вовсе,
а хранится только на телефоне). Без этого разделения любой синк захлебнётся.

`allowBackup=false` оставляем: автобэкап Google молча заливает материал в чужое облако,
ограничен по размеру и всё равно не потянет аудио. Явный экспорт честнее и надёжнее.

Бэкап v1 упаковывается в **один ZIP** (тот же формат внутри): экспорт папкой через
SAF/DocumentFile недопустимо медленный на сотнях файлов. Для v2 остаётся открытый вопрос
scoped storage: Syncthing не пишет в приватные каталоги приложений, поэтому синк-папку
пользователь выберет через SAF с persist-разрешением, а приложение будет зеркалить туда
журналы. Решается при проектировании `:core:sync` (05 §3.2).

### 5.2. Синхронизация с Mac — проектируем сейчас, строим потом

Рассмотренные варианты:

| Вариант | Оценка |
|---|---|
| Свой бэкенд (Supabase / PocketBase / CouchDB) | Работает, но: сервер, аккаунты, оплата, приложение получает `INTERNET`, материал уезжает на чужую машину. Для тетради на одного человека — несоразмерно |
| CRDT-библиотека (Automerge, Yjs) | Правильное слияние, но кросс-платформенная история для Kotlin/Swift сырая, а модель здесь не требует символьного слияния текста |
| **Общая папка + журналы операций** (Syncthing / iCloud Drive) | **Рекомендуется.** Каждое устройство пишет свой append-only журнал в общую папку; слияние = прочитать чужие журналы и применить недостающие операции. Журналы пишутся только на добавление, поэтому конфликтов на уровне файлов нет в принципе |
| Ручной экспорт/импорт | Уже есть по 5.1. Для двух устройств и одного человека этого может хватить надолго |

У рекомендованного варианта есть свойство, которое стоит дороже удобства:
**приложение по-прежнему не ходит в сеть.** Файлы в общей папке реплицирует Syncthing —
отдельная программа, к которой у приложения нет никакого отношения. Разрешение `INTERNET`
не требуется даже с синхронизацией. Изначальная цель сохраняется полностью.

### 5.3. Mac-приложение
Общий код — модуль `:core` на Kotlin Multiplatform (Room 3.x его поддерживает):
доменная модель, БД, правила переходов статусов, движок слияния. Пишется один раз.
UI на Mac — Compose Multiplatform для десктопа: для личного инструмента это в разы дешевле,
чем отдельное приложение на SwiftUI, и переиспользует уже написанные экраны.

**Что нужно сделать сейчас ради этого:** разложить проект на модули с самого начала.

```
:core:model   — чистый Kotlin, без Android. Сущности, машина состояний, правила
:core:data    — Room, репозитории, MutationSink. KMP-совместим
:core:sync    — появится в v2. Слияние журналов
:app          — Android: Compose UI, аудио, разрешения, WorkManager
:desktop      — появится в v2. Compose for Desktop
```

Стоимость сейчас: полчаса на конфигурацию Gradle. Стоимость потом: распутывание
Android-зависимостей из доменной логики по всему коду.

## 6. Изменения в плане разработки

| Этап | Что меняется |
|---|---|
| **M0** | + release-keystore и подпись в CI через GitHub Secrets; + финальное имя пакета; + разбиение на модули `:core:model` / `:core:data` / `:app`; + правило «строки только в ресурсах» |
| **M1** | + UUIDv7 вместо автоинкремента; + `deletedAt` / `updatedAt` / `deviceId` / `lamport` во всех сущностях; + аудио по SHA-256; + `MutationSink` как единственная точка записи |
| **M1.5 (новый, был M6)** | Экспорт/импорт хранилища в описанном формате + тест «полный цикл экспорт → чистая установка → импорт → всё на месте». **Смена телефона закрывается здесь** |
| M2–M5 | Без изменений |
| **M6** | Остаётся: поиск, виджет, полировка |
| **v2** | Mac-приложение (`:desktop`) + синхронизация журналами через общую папку (`:core:sync`) + Comedy Buddy |

## 7. Цена вопроса

Всё перечисленное в разделе 3 и 6 — это примерно **один дополнительный день работы на этапах
M0–M1**. Если этого не сделать и вернуться к синхронизации через год: переписывание слоя данных,
миграция всех идентификаторов на живой базе, ручное разрешение уже возникших расхождений
и почти наверняка потеря части истории версий.

Тут нет ситуации «может пригодится, а может нет» — требование названо явно.
Единственный вопрос — платить дёшево сейчас или дорого потом.
